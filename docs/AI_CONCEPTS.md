# 用 AdCraft 理解 AI 应用开发概念

## 1. 模型开发与 AI 应用开发的连接

你之前接触过数据处理、搭模型、训练和评估。AI 应用开发把已经提供的模型能力接到用户任务里，关注输入数据、检索、工具、输出、错误处理、体验和效果。

在这个项目里，Transformer 是模型内部的计算基础，`ModelClient.chat` 是使用模型能力的入口，`AIWorkflow.run` 决定什么时候调用模型以及怎样处理结果。模型本身不会自动读项目数据库，也不知道品牌文档；程序需要把数据通过消息或工具结果传给它。

| 层 | 本项目的例子 | 你需要理解的内容 |
| --- | --- | --- |
| 模型层 | 外部 LLM 和可选 embedding 模型 | 能力边界、上下文、token、输出随机性 |
| 编排层 | Agent、检索、生成、校验、repair | 每一步怎样取得依据和结束 |
| 产品层 | 对话、资料、草稿、进度、图片 | 用户怎样完成任务与修改结果 |
| 工程层 | HTTP、配置、持久化、测试 | 请求、错误、状态和可复现性 |

## 2. API、HTTP 与 JSON

API 是程序之间约定的调用接口。HTTP 是一种传输请求和响应的协议。JSON 是传输结构化数据的一种文本格式。三者不是同一个概念。

```json
{"platform": "xiaohongshu", "message": "再短一点"}
```

这是 JSON 文本。解析后，在 Python 中通常得到字典：

```python
import json

payload = json.loads('{"platform":"xiaohongshu","message":"再短一点"}')
assert payload["message"] == "再短一点"
```

`json.loads` 是文本变对象；`json.dumps` 是对象变文本。`{"x": 1}` 和 `"{\"x\": 1}"` 不同：前者是 JSON 对象，后者是内容像 JSON 的字符串。模型有时返回 Markdown 代码块，还需要合理解析或请求修复。

`GET` 用于读取，`POST` 用于提交或创建，`DELETE` 用于删除。HTTP 状态说明接口处理结果，运行状态说明后台任务结果。创建任务返回成功，不等于模型已经生成成功。

FastAPI 帮助你定义 HTTP 路由并进行请求校验。你可以先理解普通 Python 函数和模型调用，再理解路由如何把网络数据传给函数。

## 3. token、上下文与生成参数

token 是模型处理文本的单位，不固定等于一个汉字或一个英文词。消息中的系统提示、用户请求、工具描述、工具返回、历史和草稿都可能占用上下文。

上下文长度影响能放入多少资料，但不能保证模型准确使用每条资料。长历史还会增加费用、延迟和干扰。

temperature 与 top-p 等生成参数控制采样行为。它们通常在请求参数或提供方配置中设定，具体支持取决于模型 API。较低随机性有助于比较实验，不能保证事实正确，也不保证所有供应商输出完全可重复。本项目以当前 `ModelClient` 支持的配置为准，不假装支持未实现的参数。

项目返回的 `input_tokens/output_tokens` 来自供应商实际用量字段。没有真实调用时，不应该用字符数估算结果冒充账单用量。

## 4. Prompt 与结构化输出

Prompt 不是一段神奇咒语。它包括任务目标、可信输入、约束、输出形式和示例。对一个商品文案，可以分别写清：

- 商品事实：容量 400 mL。
- 用户目标：适合通勤的小红书文案。
- 品牌规则：语气自然，避免无依据的效果承诺。
- 输出格式：标题、正文、卖点、主张及事实引用。

JSON mode、schema 约束和应用校验是不同层次：

| 方法 | 可以帮助什么 | 仍可能失败在哪里 |
| --- | --- | --- |
| 提示词要求 JSON | 引导形式 | 多余解释、代码块、错字段 |
| 供应商 JSON mode | 改善 JSON 形式 | 缺字段、空内容、业务错误 |
| Pydantic schema | 检查字段和类型 | 字段值没有事实依据 |
| 业务校验 | 检查引用、数字、规则 | 隐含语义、未定义规则、遗漏 |

当模型生成 `"capacity": "500 mL"` 时，这可以是格式正确的 JSON，却与商品资料矛盾。不能用“解析成功率”替代“事实准确率”。

## 5. Embedding 与 RAG

Embedding 把文本映射为数值向量，常用于比较语义相似度。它不是从向量精确还原原文的压缩算法，也不是模型对句子的真假判断。

RAG 是先检索外部资料，再将相关资料用于生成。项目中的基本步骤是：

1. 将品牌文档切成片段并保留来源。
2. 根据当前请求检索片段。
3. 把片段和商品事实交给生成阶段。
4. 展示证据并检查输出引用。

RAG 可以增加依据、减少重复输入、使资料可更新。它仍可能检索错误、漏掉关键规则、拿到互相冲突的版本，或生成时忽略证据。没有训练模型也能使用 RAG。

商品容量等精确字段直接读取，品牌手册等长文本检索。选择数据访问方式应看数据性质，不需要把每个字段都向量化。

## 6. BM25、余弦相似度与混合检索

BM25 是关键词检索的排序方法。它考虑查询词在文档中的频率、常见程度和文档长度。中文要先处理词项，切分方式会影响结果。型号、商品词和明确规则往往适合关键词匹配。

Embedding 余弦相似度比较两个向量方向：

\[
\operatorname{cos}(a,b)=\frac{a\cdot b}{\lVert a\rVert\lVert b\rVert}
\]

例如“表达更轻松”和“语气自然”可能词不同但语义相近。真实 embedding 有机会召回；是否成功要测量。

混合检索分别保留两种排名，再用 RRF 合并。它是排名融合，不是重排模型。项目当前不应宣称已经使用专门的 cross-encoder reranker。

| 参数 | 增大时的潜在收益 | 潜在代价 |
| --- | --- | --- |
| `chunk_size` | 上下文更完整 | 噪声更多，匹配粒度粗 |
| `chunk_overlap` | 边界信息保留 | 重复片段、缓存和输入增大 |
| `top_k` | 更可能包含关键资料 | 重复、冲突、上下文增长 |

这些参数没有普遍最优值。先固定数据与指标，再比较配置。

## 7. Agent 与工具调用

固定工作流由程序决定步骤，例如“查商品→查规则→生成”。Agent 则让模型在允许工具中决定下一步。AdCraft live 使用一个有限工具循环，模型决定是否查询商品、品牌知识或上一版草稿；程序负责实际执行。

工具调用响应中的 `arguments` 往往是 JSON 字符串，需要解析和检查。工具返回的是 observation，进入后续模型消息。

```json
{
  "type": "function",
  "function": {
    "name": "search_knowledge",
    "arguments": "{\"query\":\"品牌语气规则\"}"
  }
}
```

模型输出一个工具名不等于工具已经执行。程序必须确认工具在 allowlist 中、参数合法、资源范围正确。步数上限防止循环不结束。

工具查询权限来自代码，不能来自检索文档。文档是一种输入数据，可能包含“忽略之前的要求”之类内容；这不能改变允许工具或跨品牌读取权限。这是 prompt injection 的重要边界。

## 8. grounding、幻觉与 repair

grounding 指输出与指定依据建立联系。本项目使用事实 ID、证据 ID 和数字规则检查部分联系。引用存在只是必要条件之一，还可能发生“引用真的存在，但不支持这句话”。

幻觉包括添加没有依据的参数、杜撰来源、引用不支持结论。模型能流畅表达，并不意味着它知道商品真实属性。

repair 是将具体问题反馈给模型，请它重新生成，再执行相同检查。它可能修复结构，却仍然保留语义错误。有限修复次数、清晰失败和人工检查都很重要。

模型重复尝试和网络请求重试也不同：前者换内容，后者重做一次可能相同的远端请求。两者都可能增加费用，需要记录。

## 9. Python `async`、后台任务与 SSE

`async` 函数可以在等待 I/O 时让事件循环处理其他工作。调用它通常需要 `await`。它不等于自动并行处理 CPU 密集计算，也不代表后台任务在进程重启后会恢复。

后台任务让 HTTP 创建请求快速返回，工作继续执行。生产场景通常还需要持久队列、任务恢复和并发控制。本项目是本地演示，不宣称完成分布式任务系统。

SSE 是服务器向客户端持续推送文本事件的方式。这里推送 workflow 的 snapshot、trace 和 done。token streaming 是模型一边生成一边输出 token，二者可以同时存在，但当前项目只做前者。

当前前端采用 GET 轮询，后端 SSE 可独立访问；并不是界面已经接入 EventSource。文本和图片也分别选择模式，文本 demo 不会覆盖显式选择的真实图片提供方。

断开 SSE 是连接问题，不代表任务失败。重新查询已有 `run_id` 可以检查任务结果。重新创建任务会造成重复工作。

## 10. 幂等、会话和记忆

幂等表示重复同一操作不会再产生额外的预期副作用。创建运行时携带 `request_id`，服务端可以识别重复提交并返回已有结果。

它不能自动保证外部模型调用绝不重复计费。例如供应商已收到请求但本地超时，重试可能创建第二次计算。具体需结合上游幂等支持、任务 ID 或查询能力。

会话 ID 用来连接多次运行。最近有限历史让模型理解“第二版”“再短一点”；这不是训练模型，不意味着永远记得所有对话。删除、重建会话以及改变商品都会影响可用上下文。

## 11. Trace、评测与日志

trace 是某次执行中的可观察事件序列：调用了哪个工具、取得哪些证据、校验发现什么、耗时多少。它帮助定位问题，也帮助用户知道依据。

它不应该伪装成模型真实的内部推理过程。面试时可以展示工具行为和数据流，不需要背“模型当时在想什么”。

评测回答一个具体问题：在指定样本与配置下，系统完成任务的表现怎样？

- 结构通过率：有效结构样本数 / 全部样本数。
- 事实规则通过率：通过定义的事实规则样本数 / 全部样本数。
- 检索 Recall@k：标注相关片段中，前 k 个命中多少；要说明按查询还是按片段求平均。
- 时延：分别看排队、检索、模型、校验和整体，必要时报告 P50/P95。
- 人工质量：用明确的可读性、品牌语气和可用性评分表。

规则通过不等于人工质量优秀；demo 全通过不等于 live 全通过。没有真实投放实验时，不写转化率提升。
