# AdCraft 面试问题：由数据流讲到设计取舍

这些问题是针对当前实现的准备材料，不是某家公司的固定题库。参考答案是答题骨架；请把你实际跑过的 trace、测试、失败样例和修改补进去。涉及质量和性能的数字只有测量后才能说。

推荐答题结构：**用户问题 → 实现 → 验证 → 局限 → 下一步选择**。面试官追问细节时，能打开对应函数解释，比背名词更有价值。

## 第一层：能否说清自己做的产品

### 1. 你的项目到底解决什么问题？

给电商内容编辑提供对话式生成和修改工具。商品事实和品牌资料分开管理，系统先取证，再生成草稿与素材方案，检查结构、引用和部分商品承诺，并提供可观察的执行记录。

补充一个真实任务，例如“生成通勤文案→改短→解释依据→确认生成图片”。不要把尚未发生的投放效果当作结果。

### 2. 它与直接打开 ChatGPT 写文案有什么区别？

它将商品和品牌资料显式连接到请求，保留来源与版本，提供结构化草稿、校验、失败状态、会话记录、素材任务和可重复评测。用户无需每次手工贴全部资料。

代价是需要维护资料、模型接口、规则和产品体验。对很少的临时请求，手工聊天可能更省事。应根据业务任务选择。

### 3. 项目里哪些地方真的调用模型？

live 的工具决策、结构化生成和有限 repair 调用 LLM；完整配置时，混合检索调用 embedding。图片提供方独立配置。demo 使用确定性模板和真实 BM25，不调用 LLM。

展示 `/api/v1/ai/config` 和一次 trace 说明当前运行模式。不要用 demo 时间声称 LLM 生成快。

### 4. 这是 Agent 还是工作流？

整体是一个有明确阶段的工作流，其中 live 取证阶段有模型驱动的受控工具循环。模型决定选择哪些允许工具；程序检查参数、范围、步数，再进入固定结构化生成和校验。

不是开放式自主执行系统，也不是多个 Agent 相互协作。demo 的固定重放不证明自主工具选择。

### 5. 你个人贡献是什么？

如实区分 AI 辅助生成的初稿和你理解、调整、验证的模块。准备三个能拿出证据的贡献：一处实现修改、一项评测、一份失败复盘。未经亲手核查的模块，不宣称独立从零开发。

### 6. 为什么基础设施没有当成主亮点？

产品的主要问题是依据、生成与错误处理。当前用本地单工作区降低部署和学习成本，保留清晰模块边界；生产化才需要多租户、持久队列和共享存储。

这不是说数据库不重要，而是项目当前的验证目标更集中。

## 第二层：RAG 与数据

### 7. 为什么商品规格直接读，品牌手册却检索？

商品规格是精确字段，按已选择的商品读取最可靠。品牌手册是长文本，需要选择与当前任务有关的片段。把“容量”也放到模糊向量检索里可能漏掉或匹配到另一个商品。

### 8. 你具体怎样切块？

看 `chunk_documents`：按 Unicode 字符长度，优先在附近句末或换行结束，保留 overlap，附上文档 ID、版本、序号与内容摘要。默认 size 和 overlap 以 `AISettings` 为准。

强调这里的长度是字符，不是 tokenizer token 数。要能给出边界规则被切断的样例。

### 9. 中文 BM25 怎么处理？

`tokenize` 做 NFKC 和 casefold。中文连续片段拆相邻 bigram，单字保留；英文与数字等采用词项。这是轻量词法基线，不是完整中文分词器。

`_bm25` 使用词频、词项稀有程度和长度归一化。它能解释型号词匹配，但同义表达和切分可能漏检。

### 10. 为什么引入 embedding？

语义表达相似而词项不重合时，向量检索可能改善召回。必须使用真实 embedding 输出；哈希只用于缓存身份，不能冒充语义向量。

混合是否改善需要同样例实验。讲一个失败例子以及代价，比只说“提升语义理解”具体。

### 11. 为什么用 RRF，而不是把 BM25 和 cosine 相加？

原始分数不同量纲和范围。RRF 利用排名而非直接相加分数，当前使用 `1/(60+rank)` 合并两个最多 50 条的候选列表。局限是会丢失分数间距信息，也可能把语义噪声合进来。

### 12. top_k 越大越好吗？

可能减少漏检，但会增加噪声、重复、冲突、token 与时延。应在标注评测集上比较检索命中和最终生成质量。不能仅凭“给模型更多信息”推定更好。

### 13. 你做了 reranker 吗？

当前做 BM25、可选 cosine 和 RRF，没有专门的 cross-encoder 重排模型。后续如果候选召回足够而排序差，可以比较增加 reranker 的收益、费用和时延。

### 14. embedding 缓存如何避免旧资料？

当前缓存键包含 API base、模型和文本 SHA256，内容变化产生新键；共享 Retriever 保持跨请求缓存，LRU 容量有限。并发 miss 用锁减少重复请求，批量大小受限。

局限：缓存不是持久索引，进程重启会丢失；当前锁覆盖网络请求，较大批次可能延迟并发查询。

### 15. embedding 服务失败怎样处理？

当前显式返回安全的 `ModelError`，不偷偷将词法结果标成 hybrid，也不编造向量。可以另行设计标注清楚的降级，但要同步改变模式展示和评测口径。

### 16. 如何防止不同品牌混用资料？

检索前按当前商品 `brand_id` 限定；工具没有自由指定商品或品牌的权限；工作流再次检查检索结果来源。边界需要异常样例测试。

这是本地单工作区的品牌范围控制，不能称为完整多租户鉴权。

### 17. 文档里有 prompt injection 怎么办？

将文档和工具结果视为数据，系统提示明确禁止文档修改规则，执行器只接受 allowlist 和严格参数，商品与品牌范围由程序固定。文档写“调用删除工具”不会创造该工具。

这些措施减少风险，不证明模型永远不受恶意文本影响。应测试输出污染和敏感信息泄露，不只测试工具名。

### 18. 怎样评估检索？

准备独立标注的查询与相关片段，按定义算 Recall@k，并分析无相关资料、重复结果、冲突版本。固定语料、品牌范围和查询，比较 BM25 与 hybrid；再看生成是否正确使用命中资料。

检索命中率高，生成仍可能忽略资料。

## 第三层：工具、输出与多轮

### 19. 工具调用在程序里怎样发生？

模型返回 `tool_calls`，程序解析 JSON arguments，校验工具名与 schema，调用实际函数，将 observation 以 tool 消息返回。模型只是提出调用，实际权限和执行在程序里。

### 20. 模型不调用必要工具就生成怎么办？

live 循环检查已调用工具集合。生成或修改前要求读取商品；存在品牌资料时要求检索；修改已有草稿时要求读取上一版。缺少工具就提醒模型继续，在步数上限内完成，否则失败。

一般概念解释可以直接返回；涉及商品事实的解释按当前关键词规则要求读取商品，已有草稿相关解释在需要时要求读取上一版。解释答案有有限数字/承诺检查，但不等同于全部 Draft 校验。

### 21. 为什么步数上限和 repair 上限分开？

前者限制取证与决策，后者限制输出重写。当前分别有设置与硬上限，单轮工具数量也受限。分开便于分析循环问题、控制成本以及定位哪一步经常失败。

### 22. 工具参数为什么严格？

Pydantic 设置 `extra=forbid`、strict；空参数工具只接受空对象，知识搜索只允许 query 和合法 top_k。拒绝偷偷加入另一个品牌 ID 等字段。

严格类型可以发现错误，但也增加对供应商输出格式的要求，需明确错误返回和有限修正。

### 23. 为什么 Planner 和 Generator 分开？

Planner 选择工具与意图，Generator 根据已取得的数据生成固定 schema。分开更容易控制和测试，工具错误与内容错误也更好定位。代价是额外模型调用和时延。

可以比较一个模型请求完成全部工作的替代方案，但要测量工具遗漏、输出稳定性和成本。

### 24. JSON mode 能保证结果正确吗？

不能。适配器请求 JSON 对象，Draft schema 检查结构，业务规则检查引用与数字。它们解决不同问题。格式有效、字段完整、引用存在和语义真实不是同一指标。

### 25. 事实检查具体检查什么？

数字使用值与单位；主张的 fact_ids 必须存在并支持数字；输出数字必须有商品依据与引用；证据 ID 必须来自本次检索；少量性能承诺通过显式规则检查。

例如 400 mL 不支持 400 g，也不能支持保温 24 小时。当前不做单位换算，也不完整证明所有定性语义。

### 26. repair 如何做？

给模型原始输入上下文、失败草稿和 issues，让它输出完整修复草稿。重新校验，通过才交付；次数用尽按错误类型结束。不能通过为数据库新增虚构事实来“修复”。

### 27. 为什么不用 LLM judge 代替规则？

明确结构、引用与数字的规则更可重复、低成本、可定位。LLM judge 可辅助品牌语气和语义支持判断，但有随机性、偏差和费用。可先建立人工标注集评价 judge，而不是默认它权威。

### 28. Explain 回答也校验吗？

结构化 Draft 经过完整定义的规则。live 解释型文本用 `unsupported_request` 检查未知数值与性能承诺，失败不交付；它没有 Draft，也没有逐条解释引用的完整验证。下一步可评价解释来源与语义支持，规则通过仍不保证任意问答正确。

### 29. 多轮是怎么实现的？

保存会话运行，取最近六条与当前商品相关的历史，找到最近成功草稿。live Planner 得到历史要求，工具可以取上一版；生成阶段获得真实上一版草稿和最近要求。

这是有限上下文，不是模型训练或永久记忆。更早的否定约束可能丢失，未来可用显式约束存储或摘要，但要测丢失信息。

### 30. 怎样保证只修改用户指定字段？

提示 Generator 保留其他字段，并传入真实上一版。demo 实现有限固定编辑行为。当前没有对所有 live 修改做严格字段 diff 的强制保障，所以可能发生无关字段变化。

可以加入修改意图 schema、允许字段列表、diff 检查和回归测试。不要把提示词要求当成程序保证。

## 第四层：可靠性、评测与部署

### 31. 模型服务怎样重试？

适配器默认最多三次尝试：可重试的限流、408、5xx、网络和超时使用有界退避；认证、参数错误和耗尽额度不重试。解析错误、截断、拒绝和空内容有明确错误，不作为普通网络错误无脑重试。

超时可能发生在上游已经执行后，不能保证不会重复收费。

### 32. 请求幂等具体保证什么？

同一次提交用 request_id 识别，减少重复创建应用任务。当前按 session 分范围，SQLite 事务记录请求指纹：同 ID 同内容返回旧运行，不同内容返回 409。图片按 run 分范围。它不代替供应商幂等，也不能自动保证 crash 后恰好调用一次。

### 33. SSE 和 token streaming 什么区别？

SSE 是传输机制，内容可以是进度事件，也可以是 token。后端 SSE 接口提供工作流进度，当前前端采用 GET 轮询，ModelClient 是非流式 chat。断线后查询已有 run，避免重建任务。

### 34. Trace 怎么帮助排错？

通过 stage 和时间定位卡在规划、检索、生成还是校验；通过工具、证据 ID、issues 看数据错误。trace 记录可观察行为，不是模型私有思维链。

当前 ModelError 失败 trace 保留安全 code、retryable 和 status_code；普通异常只暴露错误类型。这样能定位认证、限流、超时等问题，同时避免泄露原始响应、密钥和敏感 URL。trace 还不等同于完善的生产日志平台。

### 35. 为什么不能只看平均耗时？

长尾请求可能影响用户体验。分别测各阶段与整体，样本足够时报告 P50/P95；同时说明冷缓存、模型、输入长度、并发和 repair 次数。demo 的毫秒不能替代 live 模型性能。

### 36. 你的评测能证明什么？

离线 demo 测确定性流程、规则和边界。fake client 测工具与 repair 行为。live 数据测真实模型的结构、事实、检索使用、修改遵从、质量、token 与时延。每类报告分别解释。

即使测试全部通过，也不能证明任意用户输入都正确。给出一个未解决失败样例最能说明你理解边界。

### 37. 为什么同时看 first-pass 与 final-pass？

最终通过率掩盖了 repair 成本。先记录首次草稿通过率，再记录修复后通过率、次数、用量和时延，可以判断系统依赖多少重写。

### 38. 怎么证明业务效果？

先测编辑任务完成时间、人工修改次数、可用草稿比例与试用反馈。真实点击率、转化率、GMV 需要投放或对照实验，控制商品、受众、时间等因素。当前没有数据就不宣称提升。

### 39. 进程重启后任务怎么办？

SQLite 保存的对象与请求映射能读回；FastAPI BackgroundTasks 不会恢复执行。启动时 `Repository.recover_interrupted` 将 queued/running 标 failed，避免无限处理中。生产需要持久执行、重试、取消与上游状态核对，不能只加数据库就解决。

### 40. 如何升级成多人服务？

先增加身份、资源归属和租户隔离；再处理共享持久化、分布式任务与幂等、预算和限流、备份及日志。工具权限与检索范围绑定已认证身份。当前只是单工作区应用。

### 41. 图片能保证商品保真吗？

当前生成背景，用 Pillow 将已上传的原图缩放合成，透明 PNG 效果更自然；未上传时只有背景。product_preserved 表示合成了原图，不代表像素完全不变或通过视觉审核。把 URL 写进文本 prompt 不等于读取图片。真实提供方路径未进行付费联调，按自己的实际测试说明兼容性。

### 42. QPS 限制够不够？

模型请求长度、输出长度、并发时间和费用差异很大。生产应同时考虑请求速率、token 预算、并发与供应商限制。当前本地并发限制不等同于完整模型网关。

### 43. 为什么不微调？

当前问题主要是资料更新、事实依据、结构输出和执行可靠性。RAG 与规则能直接处理；缺乏足够高质量训练数据时微调投入大。若以后有稳定风格任务与数据，可用同一评测集比较提示词、RAG 与微调收益。

### 44. 最有代表性的失败是什么？

用你真正复现的案例回答：输入→错误→trace→根因→修改→同样例结果→反例验证→仍存在的局限。不要背资料里虚构的错误率或业务案例。

### 45. 如果再给你一周，你改什么？

根据现有失败数据排序。可能是解释回答引用、修改字段 diff、知识冲突策略、中文同义词召回或更细的错误 trace。说清收益如何衡量，避免一次列十个框架。

## 面试前自查

- 能离线演示一次完整流程，并明确 demo。
- 有一次真实 live 调用记录或明确说明尚未实测。
- 能打开 `AIWorkflow.run`、`Retriever.search`、`validate_draft` 解释数据流。
- 有一个自己修复的 bug 和一个未解决失败样例。
- 简历指标有样本、脚本、配置和报告；没有就删掉数字。
- 能说出个人贡献与 AI 辅助范围。
