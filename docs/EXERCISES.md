# AdCraft：练习、验证方法和参考答案

先做题，再看答案。每题保存输入、结果、日志或 trace、你的解释。不要只记录“运行成功”。练习用独立会话和文档，避免覆盖自己保留的样例。

## 题目

### A1：看懂请求与状态

在 demo 模式建立会话，选一个商品，提交“写一版简短文案”。记录创建请求的响应与最终 Run。回答：创建 HTTP 请求成功和文案生成成功有什么区别？`session_id`、`run_id`、`request_id` 分别做什么？

验收：你能给出真实 JSON，指出状态字段和草稿字段，无需打开源码也能解释。

### A2：JSON 解析与类型

分别尝试解析：

```python
good = '{"title":"通勤好物","selling_points":["400 mL"]}'
bad_json = '{"title":"通勤好物",}'
bad_type = '{"title":"通勤好物","selling_points":"400 mL"}'
```

解释 `json.loads` 与 schema 校验各能发现哪些错误。为什么 `bad_type` 可能是合法 JSON，却不是合法 Draft？

### A3：认识真实检索

为同一品牌添加两篇资料：“自然、轻松的表达”和“正式、专业的表达”；另给不同品牌添加一篇“夸张促销表达”。查询自然风格的规则，记录 Evidence。

验收：说明相关性、品牌过滤、来源和版本。无关品牌资料不能成为本次证据。

### A4：前端事件与模型输出

打开 Network，观察当前前端对 Run 的 GET 轮询；再手动访问 `http://localhost:8000/api/v1/ai/runs/实际run_id/events`，观察 snapshot、trace 和 done。找一条 trace 事件和一次最终草稿。回答：当前界面采用什么传输方式？后端是否逐 token 推送？断开 SSE 后，应该重新创建任务还是查询已有运行？

### B1：切块参数的对照实验

构造 600–1000 字的品牌文档，让一条规则处于可能的切块边界。尝试两组 `chunk_size/chunk_overlap`，保持查询相同。记录片段数、命中片段和重复情况。

验收：给出一个边界问题的具体样例，而不是只说“切块越小越好”。

### B2：制造事实错误

用实际商品数据构造一个结构完整的 Draft，正文和主张写“保温 24 小时”，但商品事实里没有对应内容。给 `claims.fact_ids` 写真实存在的容量 ID。

验收：调用 `validate_draft`，记录 issues。解释“引用一个真实 fact ID”为什么仍然可能不支持保温主张。再将引用 ID 改为不存在的值，比较两类问题。

### B3：有限 repair

用 fake client：第一次返回坏 JSON，第二次返回有效草稿；然后改成每次都返回坏 JSON。

验收：记录调用次数与终态。持续坏结果时，系统必须结束，并保留错误；不能无限循环。

### B4：多轮修改

同一会话先要求“写通勤文案”，再要求“更短，删掉口号”。记录第二次历史输入和输出。新会话只发送“更短”，比较结果。

当前 schema 保留 slogan 字段但允许空字符串，demo 支持删除口号。观察是否同时满足“更短”和“删口号”；live 的修改遵从仍要实际验证。

验收：指出此前草稿在哪里进入工作流。记录模型是否满足“删掉口号”，不要凭想象认为多轮一定正确。

### B5：工具边界

live 或 fake 模型返回不存在的工具 `delete_all_products`；然后返回 `search_knowledge`，但携带另一个品牌的 ID 或多余参数。

验收：系统不能执行未允许动作或越过品牌范围。记录程序返回给模型的 observation 与 trace。

### B6：重复提交

同一会话发送两次完全相同请求与相同 `request_id`；接着沿用 ID 但改变内容；最后用新的 ID 提交新内容。

验收：记录实际行为，并判断该行为是否符合 API 的当前实现。解释为什么应用端去重不证明供应商侧恰好执行一次。

### C1：建立检索小评测

准备 10 个查询，为每个标注相关文档或片段。包含型号精确匹配、同义表达、无相关资料、跨品牌词相同和多条冲突资料。

在相同语料上比较 BM25 与可用的真实 hybrid，写出 Recall@k、失败样例与耗时。如果没有 embedding 配置，就完成 BM25 对照，不伪造 hybrid 实验。

验收：清楚给出分母、数据版本和配置。结果不好也有价值，必须解释具体失败原因。

### C2：设计一个新的工具

为 `inspect_previous_draft` 以外的需求设计工具，例如查询一条已经保存的品牌规则。先写工具输入、输出、允许范围、错误和停止条件，再考虑代码。

验收：解释何时应当用工具、何时直接用当前上下文；禁止任意 URL/SQL/Python 执行。修改后给出新增行为测试与一个非法参数测试。

### C3：建立真实模型评测

从 demo 样例中选 10 条，加入 5 条你亲手发现的困难样例。明确选择 live，在固定模型和参数下运行。人工检查草稿，记录修复前后通过情况、模型调用次数和 token。

验收：报告注明“15 条样例”、模型、时间、配置、指标定义与失败样例；不把小样本结果扩展为生产级保证。

### C4：复现与修复一个问题

选你在前面发现的真实失败：漏检、空草稿、未知数字、重复工具、历史误用等。先写一个能稳定复现的测试，再修改一处核心逻辑，然后运行原样例和相关反例。

验收：保留修改前后证据，解释副作用。不要为了让一个样例通过而硬编码其完整文案。

## 参考答案与思路

下面给推理方法。具体终态、错误码和函数名称，以你运行的代码版本为准。

### A1

HTTP 创建成功意味着请求已接收或记录已创建。后台生成可能随后失败。`session_id` 连接同一对话的多次运行，`run_id` 标识一次运行，`request_id` 用于识别同一次提交的重复请求。

最终结果应查看 Run 的 `status/draft/validation/error`。只看到 HTTP 200 或 202 不能判断内容是否可用。

### A2

`good` 和 `bad_type` 都能成为 Python 对象，`bad_json` 的尾逗号会触发 JSON 解析错误。解析后 schema 才能判断 `selling_points` 应当是列表而不是字符串。项目的完整 Draft 还有其他必填字段，这些缩小样例不能直接当作完整有效输出。

可以自己执行：

```python
import json

for raw in [good, bad_json, bad_type]:
    try:
        obj = json.loads(raw)
        print(type(obj), type(obj.get("selling_points")))
    except json.JSONDecodeError as exc:
        print("JSON 格式错误", exc.msg)
```

### A3

检索只应处理当前商品品牌允许的资料。检查证据的 `document_id/title/source/version/chunk_index`，确认你可以从片段回到原文。分数是检索排序信号，不是品牌规则真实度或文案正确率。

同品牌中互相冲突的文档可能都被检索到，这需要版本或冲突策略，不能仅靠按品牌过滤解决。

### A4

后端事件流是 snapshot、trace、done，当前前端使用 GET 轮询而非 EventSource。事件显示阶段进度，不是逐 token 的语言生成。断开后查询已有 `run_id`；如果简单地重发新任务，可能导致重复生成和费用。

### B1

建议打印每片段的首尾短文本和编号，不要把整份长文档混在一起。小块可能让“禁止”和禁止内容分开；适当 overlap 能保留边界。但重叠过大会反复命中同一句话，浪费 top_k 和上下文。

你需要比较的是检索与生成行为，而不仅仅是切出了多少片段。

### B2

容量事实支持“400 mL”，不支持“保温 24 小时”。当前规则能够识别部分未知数字和引用问题；如果隐含语义错误未被识别，应记录为校验局限，而不是假称验证通过就一定真实。

引用不存在的 ID 是另一类明确的引用错误。测试时至少区分结构错误、引用错误和事实内容错误。

### B3

fake client 按调用顺序返回可预测结果，可以保证故障可重现。注意一次完整流程可能先进行工具决策，再生成和 repair；total_calls 不能简单等于 repair 次数。

把修复上限设为小值，统计生成与 repair 事件，持续失败时应进入明确终态。有限 repair 的上限既控制成本，也防止循环挂起。

下面只是 fake 的接口形态示例；测试应返回符合工具调用阶段和生成阶段的内容：

```python
class ScriptedClient:
    def __init__(self, replies):
        self.replies = iter(replies)
        self.calls = 0

    async def chat(self, messages, tools=None, json_mode=False):
        self.calls += 1
        return next(self.replies)
```

### B4

历史通过 `AIWorkflow.run(..., history=...)` 输入，其中含此前消息与草稿。运行记录完整保留，与本次只选最近历史进入上下文，是两个层次。

当前 `Draft.slogan` 允许空字符串，删除口号用 `"slogan":""` 表达，不能直接省略字段。demo 有明确删除逻辑；live 需要检查实际输出是否遵从。如果未来新增“不要图片方案”，也要一起修改 schema、生成提示、展示和回归用例，不能只隐藏界面字段。

### B5

allowlist 决定能执行的工具。工具参数只表达模型请求，不能赋予新的品牌或商品权限。服务端应绑定当前商品和品牌范围。非法输入要返回清晰 observation，并计入受限循环，防止无限重复。

### B6

当前同一会话里，同 ID 同内容返回已有执行；同 ID 不同消息返回 HTTP 409。新的意图使用新 ID。图片去重以 run 为范围，内容指纹包括方案序号。

请求映射保存在 SQLite，事务与唯一键负责去重。后台执行和会话锁仍是当前进程的；重启将未完成任务标失败。多副本执行协调、崩溃恢复和上游重复收费需要额外设计，不能把本地去重叫成分布式 exactly-once。

### C1

先写标注，再调参数，避免把答案调进评测集。记录“无相关资料”查询是否返回噪声；Recall 对无正例查询没有同样的分母，应单独统计无证据处理。

BM25 对型号精确词项可能更好，embedding 对同义表达可能更好，融合也可能引入额外无关片段。讨论具体样例比单一平均数字更有帮助。

### C2

先设计数据契约，再加入 schema 与 dispatch。工具执行结果应是可观察数据，错误也是明确数据；不能把模型生成的参数直接拼成 SQL 或 shell。

保留对新工具、非法参数、超出范围和调用上限的测试。一个工具是否有用，要看它解决哪个真实意图，而不是名字是否像 Agent。

### C3

建议同时记录 first-pass（首次草稿）和 final（repair 后）通过率。若只统计最终通过，会隐藏修复费用和时延。按问题类型拆分，说明人工审查与程序规则各发现什么。

同一模型也可能产生随机差异；需要时重复运行，但报告预算。demo 报告与 live 报告分别展示。

### C4

优秀复盘包括：触发输入、预期、实际、根因、最小修改、回归验证、仍然存在的边界。比如“中文同义词漏检”不应通过把所有文档都塞进提示词掩盖，而应比较查询或检索改进对召回、噪声、费用的影响。
